# Conventions

Durable, stable process and style rules. These don't change per-PR — if one
of them stops being true, edit it here rather than letting it drift. For
what the system looks like today, see [a_architecture.md](a_architecture.md).

## Git hard rules

- Branch per slice/milestone; commit as you go rather than one large commit
  at the end.
- Open a PR per milestone (or per meaningful slice) using the template in
  `TASKS.md` §8 — don't batch unrelated work into one PR.
- Never force-push or rewrite history on a branch someone else might be
  building on.

## Migration / schema change rules

There is no formal migration system — `lib/db.ts` is an in-memory store
seeded fresh from `lib/seed.ts` on startup. When the shape of the data
changes:
- Update `lib/types.ts` first — it's the single source of truth for shapes.
- Mirror the change in `lib/seed.ts` so seeded data still matches the types.
- Because there's no persisted schema, "migration" here just means keeping
  types and seed data in lockstep — there's no upgrade path to write.

## Branching & PR rules

- Follow `TASKS.md` §2 (ground rules) for branch naming and commit cadence.
- Every PR uses the template in `TASKS.md` §8.
- Reference which milestone (M1–M5) or stretch goal the PR covers.

## Styling rules

- CSS Modules only — no Tailwind, no CSS-in-JS, no component library.
- Every colour, space, radius, shadow, and font size comes from a token in
  `app/styles/tokens.css`. No hex codes, no magic pixel values in components.
- One `.module.css` next to each component. Nothing new goes in
  `app/globals.css`.
- Check `/styleguide` before building a new component — it probably exists.
- Both light and dark themes have to work. Tokens handle that automatically
  if you use them — don't hardcode either theme's values.
- **LTR only.** This project has no RTL requirement — don't add
  `margin-inline`/logical-property plumbing or bidi handling for RTL support
  that isn't needed; plain `left`/`right` is fine here.

## Component conventions

- `components/ui/` — generic primitives, no domain knowledge.
- `components/events/` — anything that understands the events domain.
- `components/layout/` — the app frame.
- Server Components by default. Add `"use client"` only at the leaf that
  actually needs state, an effect, or an event handler — not at the top of
  a page.
- Props are explicit. No prop spreading through several layers.

## Data and permissions

- `lib/db.ts` and `lib/seed.ts` are server only. A Client Component that
  needs data calls an API route.
- `getCurrentUser()` from `lib/session.ts` is the only source of identity
  on the server. Never take a `userId` from a request body and trust it.
- Every rule in `TASKS.md` §4 is enforced in the route handler — hiding a
  button is a UX affordance, not a permission check.
- Answer "can this person see this event" and "can this person manage this
  event" in one shared place (`lib/visibility.ts`), and call it from both
  the pages and the API.

## API routes

Follow `app/api/session/route.ts`. Every handler is wrapped in
`withErrorHandling`; bodies are read with `readJson`; anything the caller
got wrong is thrown as an `ApiError`; success returns a plain object.
Client code calls `fetchJson` from `lib/api.ts`, which unwraps the payload
and throws the server's message on failure. Route handlers, not Server
Actions — that keeps the authorization boundary a single obvious layer.

## Copy

User-facing words live in `lib/labels.ts`. Import them rather than typing
strings into JSX, so the board and the detail page never disagree about
what to call a pending request.

## Next.js version-awareness rule

This Next.js version has breaking changes vs. training data — APIs,
conventions, and file structure may differ from what you'd expect. Read the
relevant guide in `node_modules/next/dist/docs/` before writing any
Next-specific code, and heed deprecation notices. (`AGENTS.md` carries this
same reminder and is regenerated by `next dev` — don't hand-edit it.)

## Codebase-exploration rule

Before adding something new, check whether it already exists:
`components/ui/`, `lib/`, and `/styleguide` cover most primitives and
patterns already. Actively search for existing functions/utilities before
proposing new ones.

## Finishing a task

```bash
npm run typecheck && npm run lint && npm run build
```

Then click through the app as at least two personas — one organizer and
one member. Most of the bugs in this project are visible only when you
switch.
